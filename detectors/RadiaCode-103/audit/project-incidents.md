### P-001 — Кванты через открытый верх домика не записывались стадией 1 переноса
- **Дата / проект / компонент**: 2026-08-15 / RadiaCode-103 / `geometry/shieldrun.cc`, класс `TransStep`
- **Класс / подкласс**: ПРОЕКТНЫЙ / тихо неверный результат (не крашится, даёт заниженное число)
- **Внешний симптом**: расчётный фон в домике систематически ниже ожидаемого; при разборе по
  граням выяснилось, что доля потока через верхнюю (открытую) грань в CSV пересечений — 0
  независимо от геометрии
- **Воспроизведение**: `shieldrun trans` на домике с `nolid` (крышка снята) — в выходном CSV нет
  ни одной строки с гранью `+z`, хотя геометрически верх открыт и туда должен идти основной поток
- **Error verbatim**: нет — не программная ошибка, логическая. `TransStep::UserSteppingAction`
  регистрировал только переходы «слой защиты → полость» (`fGeomBoundary` с `preV` в списке слоёв
  свинца); квант, входящий через ОТКРЫТЫЙ верх, рождается сразу внутри объёма `cavity` — шага
  «слой → полость» для него не существует, и условие регистрации никогда не срабатывало
- **Root cause**: `geometry/shieldrun.cc`, класс `TransStep` — регистрация пересечения была
  завязана на предыдущий объём = слой свинца, без ветки для случая «нет слоя вовсе» (открытая
  геометрия). Верхняя грань габарита при `nolid` геометрически совпадает с верхней гранью
  полости — там просто нет вещества, через которое можно "войти"
- **Как пойман**: доля верхнего канала (K 86,8 % / Ra 89,9 % / Th 90,4 % от полного потока в
  полость) сошлась с независимым геометрическим расчётом (4,02 % площади розыгрыша → ожидалось
  40 200 квантов из 10⁶, получено 39 683-40 335) — то есть проверялась НЕ штатным тестом, а
  специально построенной перекрёстной сверкой после того, как заподозрил дыру
- **Затронутые данные**: ВСЕ прежние прогоны фона для открытой геометрии домика (до 15.08.2026)
  занижали расчётный поток в 87-90 раз по этому каналу — результаты сравнения с измерением,
  сделанные до этой даты, недействительны
- **Исправление**: добавлена обработка первого шага первичного трека, стартовавшего прямо в
  объёме `cavity` (`trk->GetParentID() == 0 && trk->GetCurrentStepNumber() == 1`) — такой трек
  регистрируется как пересечение верхней грани без требования предыдущего слоя. SHA коммита нет
  (правки в рабочем дереве, не закоммичены — оператор не давал разрешения на коммит)
- **Проверка исправления**: пересчёт с исправлением дал долю верхнего канала 86,8-90,4 %,
  совпадающую с независимым геометрическим расчётом в пределах статистической ошибки
- **Сканирование класса**: тот же класс дефекта (регистрация завязана на предыдущий материальный
  объём вместо явной обработки «нет объёма») проверен в остальных стадиях (`replay`, `resp`) —
  не найден, там источники строятся штатным GPS/`BoxSurfaceGun`, не через пошаговый перехват
- **Owner / status**: GEANT4 / **CLOSED-fixed** (не закоммичено)

### P-002 — Стадия 2 переноса (`replay`) строилась БЕЗ свинца — терялись обратное рассеяние и K-флуоресценция
- **Дата / проект / компонент**: 2026-08-15 / RadiaCode-103 / `geometry/shieldrun.cc`, флаг `withShield` в режиме `replay`
- **Класс / подкласс**: ПРОЕКТНЫЙ / тихо неверный результат
- **Внешний симптом**: расчётная модель фона систематически занижала мягкую часть спектра
  (60-95 кэВ, область K-флуоресценции свинца) против измерения; жёсткая часть (>400 кэВ) сходилась
- **Воспроизведение**: сравнение на ОДИНАКОВОМ входном файле пересечений: с `withShield=true`
  против `withShield=false` в режиме `replay` — окно 60-95 кэВ отличается в 17,2 раза
  (K-флуоресцентные линии свинца 72,8/75,0/84,9/87,3 кэВ отсутствуют в варианте без свинца),
  окно 200-400 кэВ — в 2,1 раза, выше 400 кэВ разницы почти нет (0,93-0,97)
- **Error verbatim**: нет — логическая ошибка в комментарии-обосновании кода:
  `// replay: полная геометрия (прибор+сосуд), БЕЗ свинца — его роль уже учтена тем, что до этой
  точки дошли только реально выжившие в trans пересечения.` Обоснование верно только для ПРЯМОГО
  прохождения сквозь толщу, не учитывает, что квант внутри полости может удариться в
  противоположную стенку и дать вторичное излучение (рассеяние, флуоресценция)
- **Root cause**: `geometry/shieldrun.cc`, строка с `if (mode == "replay") withShield = false;` —
  геометрия защиты не строилась в стадии 2 вовсе, хотя стадия 1 записывает лишь ФАКТ пересечения
  границы полости, а не судьбу кванта ПОСЛЕ входа в неё
- **Как пойман**: сверка расчёта с измерением показала провал модели ровно в области K-края
  поглощения свинца (72-88 кэВ) там, где у измерения максимум — целенаправленная проверка на
  минимальном контролируемом примере (одинаковый вход, только флаг свинца меняется)
- **Затронутые данные**: все расчёты фона со стадией 2 до этой правки занижали мягкую часть
  спектра (<100 кэВ существенно, до 400 кэВ заметно)
- **Исправление**: `withShield = true` для режима `replay` по умолчанию; старое поведение
  доступно явным ключом `noshield` через новый флаг `noShieldAsked` (отличает «свинца нет по
  умолчанию режима» от «оператор явно попросил без свинца»)
- **Проверка исправления**: сравнение на одинаковом входе подтвердило ожидаемый эффект (K-линии
  появились на правильных энергиях 72,8/75,0/84,9/87,3 кэВ, выше 400 кэВ поведение не изменилось —
  значит правка не сломала прямой канал)
- **Сканирование класса**: другие режимы (`trans`, `resp`, `beam`, `sample`) используют
  `withShield` иначе и не содержат того же паттерна «отключить материал под неполным
  обоснованием» — не найдено
- **Owner / status**: GEANT4 / **CLOSED-fixed** (не закоммичено)

### P-003 — Мюонный источник разыгрывал угол по интенсивности вместо потока через площадку
- **Дата / проект / компонент**: 2026-08-15 / RadiaCode-103 / `geometry/shieldrun.cc` (класс
  `MuGun`) и `geometry/cosmicmu.cc` — идентичный дефект в обоих файлах
- **Класс / подкласс**: ПРОЕКТНЫЙ / тихо неверный результат (систематическое искажение формы
  континуума, не только амплитуды)
- **Внешний симптом**: расхождение расчётной мюонной компоненты с измерением в окне 2700-2790 кэВ
  было 1,80 при подогнанной амплитуде — подозрительно велико для континуума, форма которого
  считается известной (PDG Гайссер)
- **Воспроизведение**: не воспроизводится единичным прогоном — обнаружено разбором физики
  розыгрыша, не по расхождению числа
- **Error verbatim**: нет — ошибка в формуле розыгрыша: `const double cosT = std::cbrt(G4UniformRand());`
  даёт распределение `p(cosθ) ~ cosθ²` — это распределение самой ИНТЕНСИВНОСТИ `I(θ) ~ cos²θ`,
  заданной на площадку, перпендикулярную треку
- **Root cause**: для частиц, пересекающих ГОРИЗОНТАЛЬНЫЙ диск-источник, нужен дополнительный
  множитель `cosθ` (проекция площадки на направление трека):
  `dN ~ I(θ)·cosθ·dΩ ~ cos³θ·sinθ·dθ`, то есть верное распределение `p(cosθ) ~ cosθ³` и розыгрыш
  `cosθ = u^(1/4)`, а не `u^(1/3)`. Средний косинус угла старта был 3/4 вместо верных 4/5 —
  мюоны стартовали систематически наклоннее реальных, наклонный мюон проходит больше вещества
  и даёт больший депозит энергии — искажалась форма континуума, не только амплитуда
- **Как пойман**: разбором физической постановки задачи при подготовке независимой (не
  подогнанной) нормировки мюонной компоненты по потоку PDG — не штатным тестом
- **Затронутые данные**: ВСЯ мюонная компонента во всех прежних расчётах (обоих файлов) искажена
  по форме; амплитуда `A_MU=315,2`, подобранная под измерение при старом (неверном) розыгрыше,
  впитала в себя часть этой ошибки компенсацией — использовать её после исправления розыгрыша
  НЕЛЬЗЯ, отменена
- **Исправление**: `cosT = std::pow(G4UniformRand(), 0.25)` в обоих файлах (`shieldrun.cc::MuGun`,
  `cosmicmu.cc`); амплитуда переведена на априорный поток PDG (0,0167 мюон/см²·с на
  горизонтальную поверхность на уровне моря) вместо подогнанной — свободный параметр устранён, а
  не перекалиброван
- **Проверка исправления**: отдельно перепроверено насыщение радиуса диска-источника (был
  дополнительный сопутствующий дефект — радиус 700 мм занижал отклик на 19 % на новой,
  вдвое большей геометрии домика; развёртка X=πR²·eff дала 2,013/2,498/2,448 при R=700/1000/1400,
  рабочий радиус переведён на 1000 мм). После обеих правок расхождение с измерением в окне
  2700-2790 кэВ снизилось с 1,80 (подогнанное, старая физика) до 1,25±0,10 (априорное, новая
  физика) — без единого свободного параметра
- **Сканирование класса**: дефект найден СРАЗУ в двух местах (`shieldrun.cc` и `cosmicmu.cc`) —
  оба содержали идентичный `cbrt(G4UniformRand())` для розыгрыша угла мюона; оба исправлены в
  одном заходе, не по одному
- **Owner / status**: GEANT4 / **CLOSED-fixed** (не закоммичено)

### P-004 — `replay`-биасинг падает и, вероятно, искажает вес: тонкое окно reflector без ограничения шага
- **Дата / проект / компонент**: 2026-08-16 / RadiaCode-103 / `geometry/shieldrun.cc` (importance
  biasing, `doBiasReplay`), `geometry/RCDetector.cc` (геометрия окна reflector→SiPM)
- **Класс / подкласс**: ПРОЕКТНЫЙ / крах + вероятная тихая систематика (два разных проявления
  одной причины)
- **Внешний симптом**: (1) `#SHIELD-5`, известный ранее — `replay` с биасингом падает с access
  violation ~раз в 6 прогонов; (2) НОВОЕ 2026-08-16 — в прогоне серии K (`replay_K_00.csv`) файл
  упал ТРИЖДЫ ПОДРЯД с ТРЕМЯ РАЗНЫМИ кодами возврата NT (`rc=3221226356`=0xC0000374 heap
  corruption, `3221226505`=0xC0000409 stack buffer overrun/fast-fail, `3221225477`=0xC0000005
  access violation) — сборка продолжила с 1 файлом K вместо 2, статистика серии K занижена;
  (3) сверка расчёта фона с измерением занижает результат в 3.6-4.8 раза почти во всех окнах —
  возможно та же причина искажает вес и в НЕ упавших прогонах
- **Воспроизведение**: `shieldrun.exe replay pb=50 hxcav=75 hycav=75 hzcav=192.5 seatfloor=1
  nolid in=trans_K.csv bias crystep=<X> seed=<Y> repeat=3 out=<Z>` — падает при `crystep=8.0` И
  при `crystep=2.0` (оба протестированы 2026-08-16, оба SIGSEGV/exit 139); `crystep=4.0`
  (production-значение) в тесте отработал, но с тем же предупреждением ниже
- **Error verbatim**: `*** G4Exception : GeomBias1001 issued by : G4ImportanceAlgorithm::Warning()
  Calculate() - ipre_over_ipost ! in [0.25, 4]. ipre_over_ipost = 0.125.` (при crystep=8) и
  `ipre_over_ipost = 8.` (при crystep=2) — G4 сам маркирует это только предупреждением
  («This is just a warning message»), не фатальной ошибкой, но КРАШ следует за ним в обоих тестах
- **Root cause**: **ГИПОТЕЗА, не подтверждено фиксом** (различать факт и предположение честно).
  Факт: `ipre_over_ipost=8` при `crystep=2` равно `crystep³` (2³=8) — точное совпадение, не
  визуальная похожесть. Значит где-то трек пересекает НЕ одну importance-границу за шаг
  (case→caseAir→reflector→crystal, множитель `crystep` каждая), а перескакивает несколько сразу.
  Геометрия (`RCDetector.cc:333-341`, прочитано построчно): кристалл обёрнут `reflector` со всех
  сторон, но на стороне окна к SiPM (`win=0.05`) слой — плёнка 0.05 мм. Во всей папке `geometry/`
  нет НИ ОДНОГО `G4UserLimits`/`SetMaxAllowedStep` (grep, факт) — ничто не ограничивает шаг
  трекинга гамма-кванта на этой тонкой плёнке; свободный пробег гаммы в её материале обычно
  намного больше 0.05 мм, так что квант, вероятно, пересекает плёнку целиком за один шаг,
  пропуская регистрацию промежуточной importance-ячейки `reflector` — отсюда скачок `crystep³`
  вместо `crystep`. НЕ проверено экспериментально (планируемый тест — добавить `G4UserLimits`,
  перепрогнать, смотреть исчезло ли `GeomBias1001`).
- **Как пойман**: (2) поймано проверкой файлов на диске после «завершившегося» прогона (не
  поверил, что раз процесс дошёл до конца — все 6 файлов готовы); (3) поймано сверкой с
  измерением, которую оператор явно потребовал («только честная физика», без подгонки); причина
  — целенаправленной диагностикой (три тестовых прогона с разным `crystep` на уже готовом
  `trans_K.csv`, не гадание)
- **Затронутые данные**: серия K в прогоне 2026-08-16 (статистика на 1 файле вместо 2); ВСЕ
  прежние прогоны с биасингом потенциально затронуты той же систематикой в неизвестной степени
  (не измерено — фикс не применён, сравнить before/after не с чем)
- **Исправление**: НЕ ПРИМЕНЕНО. План: `G4UserLimits(maxStep ≪ 0.05 мм)` на объём `reflector` в
  `shieldrun.cc` (секция `doBiasReplay`, ~строка 1119-1145), диагностический прогон на малой
  статистике, полный пересчёт K/Ra/Th при подтверждении
- **Проверка исправления**: не применимо — исправление не внесено
- **Сканирование класса**: не проводилось — узнать, есть ли другие тонкие (<1мм) слои в
  importance-geometry детектора без step limit (кандидаты: `sipmPcb`, стенки `case`/`caseAir`)
- **Owner / status**: GEANT4 / **OPEN** — причина вероятная, не подтверждена; #SHIELD-5 не закрыт

### P-005 — #SHIELD-16: локализация «базовая геометрия детектора» опровергнута — кристалл сходится с NIST
- **Дата**: 2026-08-16. **Симптом**: диагностика diag-маской (`RCDetector.hh fDiagMask`,
  material->воздух для case/reflector/internals) — голый кристалл (mask=7) даёт ТОТ ЖЕ дефицит
  (0.709 от паспорта), что baseline (0.774). Убирание вещества НЕ поднимает эффективность к 1.0.
- **Root cause вывода**: P(взаимодействие в кристалле) по MC ≈ 0.283-0.290 (front/back/nose,
  sens_diag_m7). Независимо: NIST XCOM CsI μ/ρ на 662 кэВ (интерполяция 0.6/0.8 МэВ, точки
  8.373E-02 и 6.769E-02 см²/г) даёт μ=0.0778×4.51=0.351 см⁻¹, P=1-exp(-0.351)=0.296 — сходится
  с MC в пределах ~4-5 %. **Кристалл физически корректен**, дефицит НЕ в геометрии/материале
  детектора вовсе.
- **Вывод**: прежняя запись «причина локализована в main.cc/RCDetector.cc» — неполная/неверная.
  Дефицит 25-35 % теперь указывает на конвенцию сравнения (паспорт 30 cps может быть не
  narrow-beam нормальный, а другая геометрия облучения) либо на неопределённость активностей
  открытого поля — не на баг модели.
- **Как пойман**: целенаправленный diag-тест (не гадание) + честная сверка с NIST (WebFetch,
  цитата таблицы), не по памяти.
- **Owner / status**: GEANT4 / OPEN — #SHIELD-16 переоткрыт в новом направлении (конвенция
  эталона, не геометрия детектора)

### P-006 — #SHIELD-16 был поставлен неверно: метод сверки СЛЕП к тому дефекту, который искали
- **Дата**: 2026-08-16. **Найдено**: стерильным разбором цепочки нормировки (субагент, бриф без
  моих выводов), подтверждено ссылками на строки кода.
- **Симптом**: месяц искали «почему модель занижает отклик на 25-35 %», опровергая гипотезу за
  гипотезой (геометрия детектора, кристалл, конвенция дозы) — все проверки давали «не здесь».
- **Root cause постановки**: активности бетона `PRIOR_BQKG` (`run_bg_shield.py:63`) получены
  ДЕЛЕНИЕМ измеренной площади линии на МОДЕЛЬНЫЙ отклик той же линии (`fit_lines.py:158`).
  Обе операции линейны по модели, поэтому **равномерный множитель K сокращается тождественно**:
  занизила модель отклик в K раз → активность завысилась в K раз → предсказание вернулось к
  истинному. **Сверка открытого фона физически НЕ МОЖЕТ показать равномерный дефект отклика.**
  Искали то, чего метод не показывает в принципе.
- **Следствие 1 — «континуум 0,70» не континуум**: окно `("полный 20-3000", 20.0, 3000.0)`

### P-009 — Схема важностей `doBiasReplay` жёстко привязана к ВЕРТИКАЛЬНОЙ посадке прибора
- **Дата**: 2026-08-17. **Компонент**: `geometry/shieldrun.cc`, `doBiasReplay`.
- **Симптом**: при горизонтальной посадке (`horiz=1`, P-008) прогон `replay` с `bias`
  выдаёт `G4Exception GeomBias1001: ipre_over_ipost = 0.0625` и падает без выходного
  файла. В вертикальной на том же входе — работает.
- **Root cause**: `0.0625 = 1/4² = 1/crystep²` при `crystep=4.0` — трек пересекает СРАЗУ
  ДВЕ границы важности вместо одной. Цепочка ячеек (`case` → `caseAir` → `reflector` →
  `crystal` плюс соседи `caseAir`, исправленные в #SHIELD-14) строится по геометрическому
  расположению объёмов, которое при повороте `case` на −90° меняется: то, что было
  последовательным проходом вдоль оси прибора, становится проходом поперёк, и часть
  ячеек трек проскакивает за один шаг.
- **Класс**: тот же, что #SHIELD-14 (P-004) — обрыв важности, но по другой причине:
  там были не охваченные соседи, здесь — смена геометрии под неизменной схемой.
- **Следствие для работы**: сравнение ориентаций сделано БЕЗ биасинга (все конфигурации
  в равных условиях, статистика ниже, но выводы сравнительные — годятся). Для
  ПРОДАКШЕН-расчёта в горизонтальной посадке схему важностей придётся перестраивать под
  новую геометрию, иначе биасинг неприменим.
- **Owner / status**: GEANT4 / OPEN — блокирует продакшен-прогон горизонтальной посадки.

**P-009, дополнение 17.08 02:20 — механизм разобран точно, исправление написано:**
`0,0625 = 1/4² = 1/cryStep²` — трек переходил из ячейки важности 1 сразу в `caseAir`,
**минуя `case`**. Причина не в схеме важностей (она по вложенности объёмов и при повороте
не меняется), а в ГЕОМЕТРИИ ПУТИ: вертикально стоящий прибор квант проходил вдоль оси
через нос/хвост (`wallNose`/`wallTail` = 2,0 мм), лёжа — входит через большую грань, где
`wallFace` всего **1,50 мм**. Свободный пробег гамма в ABS на сотнях кэВ — сантиметры,
поэтому такую стенку трек проскакивает целиком за один шаг, промежуточная ячейка не
регистрируется, `G4ImportanceAlgorithm` видит скачок через уровень.

Исправление (написано, СБОРКА НЕ ЗАВЕРШЕНА — бинарник занят работающими прогонами):
1. `G4StepLimiterPhysics` в физлист `Phys` — без него `SetMaxAllowedStep` молча
   игнорируется, процесса-исполнителя не существует. Это же объясняет, почему аналогичная
   мера, предложенная в P-004 для плёнки `reflector`, тогда не сработала бы.
2. `G4UserLimits(0,25 мм)` на все четыре объёма пути важности (`case`, `caseAir`,
   `reflector`, `crystal`). 0,25 мм даёт ≥5 шагов на пересечение самой тонкой стенки
   (1,50 мм `wallFace`, 1,25 мм `reflector`).
Побитово прежнее поведение вне биасинга: `G4StepLimiterPhysics` без `G4UserLimits` не
делает ничего, лимиты ставятся только внутри `doBiasReplay`.

**Приёмка (#SA-3, ещё не выполнена):** горизонтальный прогон с биасингом обязан пройти
БЕЗ `GeomBias1001`; мутация — убрать `SetUserLimits`, предупреждение обязано вернуться.
Если оно не возвращается, значит лечило не это.

### P-013 — Ключ `lift=` задавал не тот зазор, который называл оператор
- **Дата**: 2026-08-17. **Компонент**: `geometry/shieldrun.cc`, `geometry/RCDetector.cc`.

  версия пересчёта была этим же замером и отвергнута — проверка сработала до счёта.
- **Затронуто**: все прогоны `pbself` от 17.08 13:50 (пять ячеек свинца) считались с
  `lift=25`, то есть с зазором 28,25 мм вместо 25. Эффект на результат мал (расстояние до
  дна изменяется на 3,25 мм при габарите полости 385 мм), но пересчёт нужен для чистоты.
- **Сканирование класса**: искал другие ключи, чьё ИМЯ обещает физическую величину, а
  значение задаёт внутреннюю координату. `zcav=` защищён явной оговоркой про `seatfloor=0`;
  `rdisk=`, `hxcav/hycav/hzcav` — прямые габариты, подмены смысла нет. Общая мера шире

  источника. Соло-прогон упавшего макроса (Ac228) без всякой конкуренции падал тем же

  точек — зелёный прогон. Далее бинарный перебор на границе: **1024 точки → код 0,
  1025 точек → STATUS_STACK_BUFFER_OVERRUN (-1073740791)**. Похоже на фиксированный массив
  где-то в реализации GPS Arb-гистограммы этой сборки G4 11.2.1 — не в проектном коде,
  чинить нечего, только не превышать.
- **Почему возникло именно сейчас**: сетка флюенса при переходе на 2 кэВ/канал (ради формы

  порождала физически (там были ~80 дискретных линий).
- **Как пойман**: сторожем FLUENCE_ZERO НЕ пойман (это другой класс ошибки — здесь
  результата вообще нет, процесс падает, а не тихо даёт ноль); пойман падением кода
  возврата, которое НЕ было проигнорировано, потому что за каждым прогоном следует чтение
  .log-файла, а не доверие коду запуска (#SA-1).
- **Исправление**: `rebin_for_gps()` в `make_ion_macros.py` — переменное разрешение:
  точная 2-кэВ сетка НИЖЕ 200 кэВ (там живёт K-X комплекс, ради которого сетку мельчили),
  окна 10 кэВ ВЫШЕ (детектор с ПШПВ в десятки кэВ там всё равно не различит 2 кэВ).
  Сумма потока внутри окна, а не среднее — интеграл сохраняется точно. Гейт в `main()`:
  если после ребиннинга всё ещё >900 точек (запас от границы 1024) — `sys.exit(3)`, макрос

- **Проверка меры (#SA-3, мутационная)**: (1) сама функция проверена на синтетике 2000
  точек — дрейф суммы 0,00e+00, монотонность сохранена; (2) гейт в `main()` намеренно
  сломан (подмена `rebin_for_gps` на версию, искажающую сумму, + принудительно частая
  ветка) — гейт сработал, `sys.exit(3)` с сообщением о дрейфе; откат подмены выполнен.
  На реальных данных: все 8 нуклидов сократились с 1038–1306 точек до 321–341, далеко от
  границы; сумма потока не менялась (сохраняется по построению функции).
- **Сканирование класса**: лимит 1024 — свойство ДВИЖКА, не только ионного режима.
  Табличный режим (`nuc=`) физически не порождает столько точек (таблица ~80 линий), но
  если когда-либо появится источник с более широким дискретным набором линий — тот же
  гейт нужен и там. `MAX_HIST_POINTS` вынесен константой в начало файла для переиспользования.
- **Owner / status**: GEANT4 / CLOSED-fixed. Перепроверка — восемь детекторных прогонов

### P-023 — Метод 1 без nucleusLimits: шаблон звена вбирал всю цепочку потомков

- **Дата**: 2026-08-21. **Компонент**: `geometry/wallfield.cc`, метод 1 (МК-шаблоны по нуклидам).

### P-024 — Совместная NNLS-подгонка по линиям (`fit_by_lines`) уязвима к шумным
кросс-элементам матрицы у слабых по потоку звеньев

- **Дата**: 2026-08-22. **Компонент**: `analysis/fit_nuclides.py`, функция `fit_by_lines`.
- **Симптом ВНЕШНИЙ**: совместная система (NNLS по узким линиям, `cond=6,2`) даёт
  K-40=145,29±6,90 Бк/кг — заметно ВЫШЕ, чем разделение «поодиночке» без учёта
  интерференции (129,2±6,1) и чем независимый метод моноотклика (122,1±5,8,
  D-002/anchor). Интуитивно ожидалось обратное — учёт чужого вклада в грязное окно
  K-40 должен УМЕНЬШАТЬ чистую амплитуду, не увеличивать.
- **Root cause**: прямым выводом полной матрицы `M[линия][звено]` (одноразовый
  debug-print, откачен после проверки — не оставлен в коде) найдено: элемент
  Th-232→окно K40(1460,8 кэВ) = **-1,405e-04**, ПО МОДУЛЮ В 4,4 РАЗА БОЛЬШЕ

  не физика (отклик не может быть отрицательным), а статистический шум: `net_window`
  вычитает линейную подложку по боковым окнам из ПОЛНОГО (не моноэнергетического)
  МК-шаблона Th-232 в узкой чужой области; Th-232 — самый слабый по потоку из трёх
  родительских нуклидов, его статистика в узком чужом окне недостаточна (тот же
  класс проблемы, что D-002 уже документировал для линии 2614,5 — «шаблон шумнее
  измеряемого»). Именно этот шумный элемент «толкает» NNLS-решение K-40 вверх,
  компенсируя фиктивный отрицательный вклад Th-232 в уравнении для его строки.
- **Как пойман**: замечание оператора о нефизичности плана «зафиксировать K-40 по
  линии, Ra-226 по остатку» («хвост радия накладывается на калий») → научный поиск
  метода в литературе (IAEA spectral stripping) → обнаружение уже существующей
  реализации в проекте (`fit_by_lines`) → честный вопрос «почему число выше, а не
  ниже» → прямой вывод матрицы вместо гадания.
- **Затронутые данные**: результат `fit_by_lines` (K-40=145,29, Ra-226=3,75,
  Th-232=3,81) — под сомнением как финальная фиксация, пока проблема не решена;
  предыдущие методы (anchor, «поодиночке») этой конкретной проблемой не затронуты
  (не строят кросс-матрицу совсем), но и не учитывают интерференцию.
- **Исправление**: НЕ ВНЕСЕНО. Кандидаты: (а) увеличить МК-статистику Th-232 (и,

  (по σ) кросс-элементы матрицы вместо использования сырого (возможно шумного)
  значения; (в) зафиксировать anchor как консервативный вариант, не дожидаясь
  устранения проблемы NNLS-метода.
- **Проверка**: не применимо — исправление не внесено.
- **Сканирование класса**: не проводилось. Кандидат для общего класса ошибок
  (`~/.claude/references/error-classes.md`, доктринальный уровень) — сигнатура
  «weighted least-squares/NNLS матрица, построенная из МК- или иных статистически
  ограниченных шаблонов, содержит слабые кросс-элементы неопределённого знака,
