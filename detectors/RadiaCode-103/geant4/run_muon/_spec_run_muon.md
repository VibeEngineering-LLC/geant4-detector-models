# Спека `run_muon/` — отклик НОВОЙ GDML-модели RC-103 на космические мюоны

Мюонный столбец для нуклидного разложения фона. Считается на той же
провалидированной геометрии, что и `run_field/`.

## Физика источника (переиспользована как ДАННЫЕ, §33)

Спектр Гайссера, вертикальное приближение (PDG RPP2020 §30.3.1):

```
dN/dE dOmega = 0.14 * E^(-2.7) * [ 1/(1 + 1.1*E/115) + 0.054/(1 + 1.1*E/850) ]
```
E в ГэВ. Диапазон розыгрыша **0.3 … 100 ГэВ**, логарифмическая сетка не менее
400 узлов, кумулятивное распределение, розыгрыш двоичным поиском.

⚠ Оговорка первоисточника, повторить её комментарием в коде: формула строго
применима при E > 100/cosT ГэВ, а нас интересуют сотни МэВ — единицы ГэВ, то
есть это ЭКСТРАПОЛЯЦИЯ. Годится для формы континуума, не для абсолютного числа
с точностью до процентов.

**Угловое распределение — критическая деталь, легко ошибиться:** интенсивность
I(θ) ~ cos²θ задана на площадку, ПЕРПЕНДИКУЛЯРНУЮ треку. Через
ГОРИЗОНТАЛЬНУЮ площадку проходит dN ~ I(θ)·cosθ·dΩ ~ cos³θ·sinθ·dθ, поэтому

```cpp
const double cosT = std::pow(G4UniformRand(), 0.25);   // p(cosT) ~ cosT^3
```
Именно `0.25`, НЕ `cbrt`. В прежней реализации там стоял `cbrt` (p ~ cos²θ),
мюоны стартовали наклоннее реальных и континуум искажался — ошибка была
найдена и исправлена 15.08.2026, не повторять её.

Частица — `mu-`. Энергия и угол разыгрываются НЕЗАВИСИМО (упрощение заявлено
явно: в самой формуле E и θ связаны через E·cosθ; разъединение оправдано тем,
что вход и так экстраполяция, и добавлять точную 2D-связь означало бы ложную
точность поверх приближения).

## Геометрия источника

Горизонтальный диск радиуса `R_DISK` на высоте `Z_DISK` над прибором, мюоны
летят вниз.

```cpp
const double r  = R_DISK * std::sqrt(G4UniformRand());   // равномерно по площади
const double ph = twopi * G4UniformRand();
pos = G4ThreeVector(r*cos(ph), r*sin(ph), Z_DISK);
dir = G4ThreeVector(sinT*cos(phd), sinT*sin(phd), -cosT);
```

⚠ **Ориентация прибора в НАШЕЙ модели другая, чем была в старой.** В
`RC103_detector.gdml` корпус `Case_outer` — 123 × 34 × 17.5 мм с центром в
(0,0,0), то есть длинная ось идёт по **X**, а по Z прибор всего ±8.75 мм.
Поэтому:
- `Z_DISK = 100.0` мм — заведомо выше прибора;
- `R_DISK` по умолчанию **150.0** мм (проекция прибора в плоскости XY имеет
  полудиагональ sqrt(61.5² + 17²) = 63.8 мм, диск должен накрывать её с
  большим запасом на наклонные треки).

**`R_DISK` обязан переопределяться ключом CLI** — см. проверку насыщения ниже.

Мир: `G4Box` из `G4_AIR`, полуразмер должен вмещать диск и запас — 400 мм.

## Нормировка

Отклик считается **НА ОДИН МЮОН, пересёкший диск**, и НЕ добивается до
абсолютного потока. То есть в выход пишется `per_muon = counts / n_events` —
вероятность отклика. Амплитуда (сколько таких мюонов в секунду) подбирается
потом NNLS вместе с активностями.

Справочная проверка порядка величины (печатать, но НЕ использовать как
ограничение): интегральный поток мюонов на уровне моря ≈ **0.0167 см⁻² с⁻¹**
через горизонтальную площадку, откуда ожидаемое число через диск
`N_pdg = 0.0167 * pi * (R_DISK/10)²` в секунду (R_DISK в мм → см).

## Физ-лист

**`FTFP_BERT`**, не `G4EmStandardPhysics_option4`: мюону нужны ионизация,
тормозное, образование пар и распад, плюс адронное взаимодействие. Это
единственное место, где run_muon расходится с run_field по физике.
`SetDefaultCutValue(0.05*mm)` — как в run_field.

## Скоринг и выход

Энерговыделение в `Crystal_log` за событие (тот же паттерн, что run_field).
Гистограмма **1 кэВ/бин, 0..2999 кэВ** — та же сетка, что у нуклидных
шаблонов, иначе их нельзя будет сложить в одну матрицу.

⚠ У мюона депозиты доходят до десятков МэВ (сквозной трек через 1 см CsI даёт
~5-8 МэВ). Всё, что выше 2999 кэВ, обязано попадать в **счётчик переполнения**
`n_overflow`, а не молча теряться и не сваливаться в последний бин. Число
переполнений печатать и писать в CSV.

CSV: блок `metric,value` (`n_events`, `n_hits_in_crystal`, `n_overflow`,
`r_disk_mm`, `z_disk_mm`, `disk_area_cm2`, `pdg_expected_per_s`,
`e_lo_gev`, `e_hi_gev`), затем блок `bin_keV,counts,per_muon`.

CLI: `rc103_muon.exe <n_events> <out_csv> [rdisk=<мм>]`

## Проверка насыщения по радиусу диска — ОБЯЗАТЕЛЬНА

Известно (из опыта контура), что слишком узкий диск обрезает наклонные треки
и занижает форму континуума в полосе 700-2400 кэВ на 16-27 %. Поэтому:

1. Прогнать **3·10⁷** событий при `rdisk=150`.
2. Прогнать **3·10⁷** событий при `rdisk=300`.
3. Сравнить НОРМИРОВАННЫЕ НА ЕДИНИЦУ формы (`per_muon / sum(per_muon)`) в
   полосах 700-1500, 1500-2400, 2400-2999 кэВ.
4. Если формы расходятся более чем на 5 % — насыщение НЕ достигнуто, сделать
   третий прогон при `rdisk=600` и сказать об этом прямо в отчёте.
   Если сходятся — зафиксировать `rdisk=300` как рабочий и привести числа.

Это не формальность: результат определяет, каким шаблоном мы будем пользоваться.
Не подгонять вывод под «сошлось» — привести фактические проценты расхождения.

## Приёмка

1. Оба (или три) прогона завершились `EXITCODE=0`, без FATAL-исключений.
2. Приведены `n_hits_in_crystal` и `n_overflow` по каждому прогону.
3. Приведены фактические проценты расхождения форм по трём полосам.
4. Приведено `pdg_expected_per_s` для рабочего радиуса.
