## Записи

### P-001 — Материал `G4_Si` в GDML самоссылался, парсинг падал `0xC0000005`
- **Дата / проект / компонент**: 2026-08-26 / RadiaCode-110 / `geant4/gdml/detector/RC110_detector.gdml`, блок `<materials>`
- **Класс / подкласс**: ПРОЕКТНЫЙ / крашится, не тихая ошибка
- **Внешний симптом**: `gdml_vis.exe RC110_detector.gdml ...` падал access violation сразу
  после предупреждения `G4Exception mat031: For material G4_Si sum of fractional masses 0 is not 1`
- **Воспроизведение**: любой запуск `G4GDMLParser::Read()` на этом файле (или на минимальном
  синтетическом GDML с одним материалом `<material name="X"><fraction ref="X"/></material>`,
  где имя материала совпадает с именем ссылки на составляющую)
- **Error verbatim**: `G4Exception mat031: For material G4_Si sum of fractional masses 0 is not 1` → сразу после — `0xC0000005` access violation
- **Root cause**: строки 56-59 (до правки) —
  ```xml
  <material Z="14" name="G4_Si" state="solid">
    <D unit="g/cm3" value="2.33"/>
    <fraction n="1" ref="G4_Si"/>
  </material>
  ```
  `G4Material` регистрируется в глобальной таблице материалов Geant4 СРАЗУ в конструкторе, ДО
  заполнения состава. `<fraction ref="G4_Si">` внутри материала С ТЕМ ЖЕ ИМЕНЕМ `G4_Si` находит
  САМ СЕБЯ (ещё пустой, состав не заполнен) вместо настоящего NIST-материала кремния — self-
  reference на неготовый объект, сумма массовых долей = 0, крах позже при использовании
  материала. Проверено чтением исходника `source/persistency/gdml/src/G4GDMLReadMaterials.cc`
  (не по памяти о поведении парсера).
- **Как пойман**: побочный факт при пересборке Geant4 с GDML (§AUD-5, отдельная задача) —
  первый в истории проекта реальный прогон файла через `G4GDMLParser` (раньше GDML-модуль
  отсутствовал в сборке, файл никогда не парсился штатно). Изолировано минимальным синтетическим
  GDML-репро (один материал), не гаданием по логам крупного файла.
- **Затронутые данные**: ничего расчётного — GDML-файл никогда не использовался ни в одном
  физическом прогоне (GDML был недоступен весь проект), только для документации/векторной
  проверки экспорта. Правка чисто корректирующая, не меняет ни один объём/позицию/материал по
  составу — только убирает самоссылку.
- **Исправление**: удалено локальное переопределение `<material name="G4_Si">` целиком —
  `materialref="G4_Si"` у `SiPM_log` резолвится автоматически через `G4NistManager` (проверено
  по исходнику: `G4GDMLReadMaterials::GetMaterial()` сначала ищет уже построенный материал по
  имени, при неудаче — `G4NistManager::FindOrBuildMaterial(ref)`, что и есть точно тот же NIST
  `G4_Si`, который был бы получен явным переопределением с идентичной плотностью 2.33 г/см³ —
  то есть удаление СТРОГО эквивалентно исходному намерению, не меняет физику).
- **Проверка меры**: мутационная — тот же `gdml_vis.exe` на ИСПРАВЛЕННОМ файле: раньше падал,
  теперь `EXITCODE=0`, реальный PNG-рендер (wireframe, 1600×900), топология геометрии видна и
  соответствует ожиданиям (корпус, капсула у левого торца, плата/АКБ вдоль корпуса, вырез USB
  справа) — не просто «код возврата 0», а факт: файл создан, открыт, содержимое проверено глазами.
- **Сканирование класса**: остальные материалы файла (`G4_AIR`, `G4_CESIUM_IODIDE`, `ESR_foil`,
  `Case_ABS`, `PCB_FR4`, `LiPo_DTP962565`, `LCD_stack`, `Display_window_PC`, `USB_connector`) —
  проверены Grep на паттерн «имя материала совпадает с любым `ref=` внутри собственного блока»:
  ни один не совпадает (все ссылаются на элементы `G4_N`/`G4_O`/`G4_Cs`/`G4_I`/`G4_C`/`G4_H`
  и т.д. — других имён, не самих себя). `G4_Si` был уникальным случаем именно потому, что это
  единственный ОДНОэлементный материал, названный ТОЧНО как единственная составляющая.
