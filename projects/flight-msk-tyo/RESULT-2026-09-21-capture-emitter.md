# Результат: собственный эмиттер захватных каскадов (вариант 2, решение оператора 2026-09-21)

**Статус на 2026-09-21 ~00:45: эмиттер (C++) принят на игрушечной базе с аналитическим ответом; построитель боевой базы — в работе.**

## Зачем

Geant4 11.4.2 не применяет данные захвата из G4NDL (`RESULT-2026-09-20-step0-capture-lines.md`, раздел «ПРИЧИНА»): линия Fe 7631 кэВ в данных 0,155, в расчёте 0,0030.
Вариант 2: на каждый захват нейтрона заменять штатные гамма каскадом из базы IAEA PGAA (первичные переходы) и схемы уровней ENSDF (всё ниже).

## Принято

| Часть | Файл | Как принято |
|---|---|---|
| Разбор схемы уровней | `scripts/capture_levels.py` | независимый счёт `awk` совпал по уровням и переходам для 6 ядер (Al-28: 120/217; Fe-57: 180/235; Cu-64: 278/620; Cs-134: 122/327; I-128: 435/562; H-2: 1/0); 2 красных теста (обрезанная строка уровня, переход раньше уровня) отказали кодом 2 |
| Чтение данных | `scripts/capture_data.py` | Sn: Al-27 7725,173, Fe-56 7646,172, H-1 2224,566 кэВ; H-2: одна линия 2223,248 кэВ, σγ = 0,3326 б — совпадает с отчётом B и с независимой выкладкой |
| Эмиттер каскадов | `src/capture_emitter.hh` | игрушечная база `tables/toy_capture_db.txt` с ответом, посчитанным ДО запуска (таблица ниже); 3 мутации краснеют |
| Обёртка Geant4 | `src/capture_step.hh` | написана и прочитана; в Geant4 ещё не запускалась |

**Игрушечный тест** (4·10⁶ захватов, Wp = 0,8, Sn = 8000 кэВ; ответ выведен вручную из схемы):

| Величина | Ожидание | Получено |
|---|---|---|
| доля покрытых захватов | 0,8000 | 0,800067 |
| гамма на покрытый захват | 2,15625 | 2,15613 |
| линия 6997 кэВ (первичная на уровень 1000) | 0,7500 | 0,74994 |
| линия 7697 кэВ (первичная на уровень 300) | 0,2500 | 0,25006 |
| линия 700 кэВ | 0,5625 | 0,56222 |
| линия 300 кэВ (α = 1, конверсия 50 %) | 0,40625 | 0,40619 |
| линия 1000 кэВ | 0,1875 | 0,18772 |
| максимальная невязка баланса энергии | — | 0,047 кэВ (отдача каскадных гамма не учитывается) |

**Мутации** (по #SA-3; каждая обязана быть видна в тесте): (1) выбор первичного уровня по `u·Wp` (старый дефект) — доля уровня 2 стала 0,937 вместо 0,750;
(2) энергия перехода = вероятность — линии на 0 и 1 кэВ вместо 700 и 300; (3) конверсия отключена — линия 300 кэВ 0,812 вместо 0,406, гамма на захват 2,56 вместо 2,16. Все три краснели.

## Дефекты сгенерированного кода (найдены чтением, исправлены)

`capture_emitter.hh` (4 дефекта): энергия перехода не сохранялась (в каскаде использовалась вероятность как энергия); теги `PRI`/`TR` не читались
(любая база отказывала «ошибка чтения PRI»); тег `END` считался неизвестным; при отсутствии уровня подставлялась `Sn`.
`capture_step.hh`: удалялись только гамма штатного каскада, конверсионные электроны и рентген оставались (двойной счёт энергии) — теперь удаляются все вторичные, кроме остаточного ядра.
`emitter_selftest.cpp`: компаратор сортировки использовал переменную вне области видимости.
`build_capture_db.py` (2 попытки) и `capture_build.py` (1-я попытка): формат базы не соответствовал спецификации, `sigma0` по позиции списка,
чтение Excel на каждый изотоп, неверные индексы уровня — отбракованы.

## Процессное

* Субагент по `build_capture_db.py` упёрся в `delegation_guard`: хук блокирует запись кода ≥ 25 строк и у субагента (ступень 3 лестницы). Обхода не делал.
  Рабочий путь — дробление ЗАДАЧИ на модули с отдельными спецификациями и независимой приёмкой каждого (здесь: `capture_levels`, `capture_data`,
  `capture_build`); это не то же самое, что дробление кода ради порога (`W-124`). Урок передан внутренний аудиту (`audit/lessons-inbox.md`).

## Не проверено

* `capture_step.hh` не запускалась в Geant4; корректность подмены вторичных на шаге (`fpSteppingManager->GetfSecondary()`) — открытый вопрос.
* Боевая база: построитель ещё не принят; покрытие `Wp` по изотопам неизвестно.
* Независимая проверка на реальной схеме (Al-28, Fe-57): нужна после приёмки построителя.
