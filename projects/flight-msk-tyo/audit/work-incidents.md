# Рабочие инциденты проекта flight-msk-tyo (W-NNN)

## W-001. Off-by-one в числе бинов графика (page.js) — правый край рисовался NaN

**Найдено:** аудитом кода (внешний код-аудит), 22.09.2026, `20260922-flight-msk-tyo-audit-gotovo.md`.
**Причина:** `web/flight-dad-sgn/page.js:7` считал число бинов по формуле
`Math.round((10000 - E0) / dE) + 1` = 9981, а реальный массив данных
(`make_page_data.py`, `range(emin, emax)`) содержит 9980 элементов. Последний
индекс графика указывал за пределы массива → `undefined`/`NaN` на энергиях
у 10000 кэВ.
**Мера:** `n` берётся из фактической длины серии `total.y.length`, а не
пересчитывается по `E0/dE` — устойчиво к будущим изменениям диапазона.
**Проверка:** в браузере (`javascript_tool`) — старая формула 9981, реальная
длина 9980, подтверждено расхождение; консоль чистая после фикса, страница
пересобрана и опубликована (v20).
**Класс:** несинхронизированный дубль константы диапазона между Python
(генератор данных) и JS (потребитель) — при будущих правках диапазона
(`--emin`/`--emax` в `make_page_data.py`) сверять `n` в page.js не потребуется
(теперь читается из данных), но при появлении НОВЫХ формул на основе E0/dE
в других местах page.js — проверить тем же способом.

## W-002. `stage2_run.ps1` — устаревший скрипт не защищён от бага занижения ℓ

**Найдено:** аудитом кода (внешний код-аудит), 22.09.2026, там же.
**Причина:** `src/cabin_stage2.cc:52` — дефолт окна воспроизведения
`CABIN_ELL_CM=30`, что даёт занижение результата на 21–22 %
(`audit/calc-sterile-2.md:62`). Актуальный прогонный скрипт `stage2_k.ps1`
и `fuel_variant.ps1` жёстко выставляют `CABIN_ELL_CM=120`, но более старый
`stage2_run.ps1` (предшествовал K-кратной схеме) этого не делал — при запуске
напрямую тихо использовал бы заниженное значение.
**Мера:** в `stage2_run.ps1` добавлена проверка — если `CABIN_ELL_CM` не
задан переменной окружения, скрипт громко предупреждает (`Write-Warning`) и
сам подставляет рабочее значение 120.
**Проверка:** опубликованный `REPORT-2026-09-21-dad-sgn.md` получен через
`stage2_k.ps1` (там ℓ=120 стоит явно) — заниженного результата в
опубликованных числах нет. Подтверждено Grep по обоим прогонным скриптам.
**Класс:** несколько путей запуска одного и того же расчёта с разными
дефолтами критичного параметра — при появлении НОВОГО скрипта запуска
этапа II сверять, что `CABIN_ELL_CM` выставлен явно, а не наследуется от
дефолта C++.

## W-005. Колонка «Выход на 100 захватов» в сводке — мусор у (n,n′) реакций

**Найдено:** оператором (скриншот), 22.09.2026, сразу после публикации ред. 4.
**Причина:** в `scripts/neutron_lines_summary.py` фильтр «выход осмыслен только для (n,γ)» (введён в W-004 для
`lines_report.py`) НЕ был продублирован в саму сводку — `yld = (r.get("yield") or "").strip()` брал поле
`yield` без проверки типа реакции. Для строк (n,n′) поле `yield` в источнике хранит СЕЧЕНИЕ (мб при энергии,
формат «σ 868 мб @2 МэВ»), а не процент выхода — в колонку попадал нечитаемый текст.
**Мера:** добавлен тот же фильтр `NEUTRON_CAPTURE_RE` — для не-(n,γ) строк колонка показывает «—».
**Проверка:** в браузере (`javascript_tool`) по всем 150 строкам таблицы — регэксп `/мб|@\d|МэВ/` на колонку
«Выход» даёт 2 совпадения (было ~15), и оба — легитимные (n,γ) с честной оговоркой про малое полное сечение
элемента, не мусор.
**Класс:** тот же класс, что W-004 (поле, применимое к подмножеству, использовано без проверки применимости) —
но повторился в ДРУГОМ месте кода, куда было скопировано то же поле `r["yield"]`. Фильтр защиты стоило сразу
делать общей функцией, а не копировать regex в два файла — при следующей правке подобного места вынести
`is_capture_reaction()` в `bline_table.py`, чтобы не разошлись снова.
**Опубликовано:** версия 25 той же ссылки.

## W-004. Подпись «выход на 100 захватов» прицепилась к не-захватным реакциям

**Найдено:** самопроверкой в браузере сразу после правки (не аудитом внешний код-аудит), 22.09.2026, в рамках #REM-1.
**Причина:** [scripts/lines_report.py](scripts/lines_report.py) добавлял `line["yield"]` к тексту реакции для
ВСЕХ строк таблицы `B-gamma-lines-airframe.md` без проверки типа реакции — поле `yield` заполнено у каждой
строки (не только у (n,γ)), поэтому подпись «выход на 100 захватов: …» появилась и у 511 кэВ (аннигиляция
позитронов) и у 1460,82 кэВ (распад K-40), где понятие «захват» физического смысла не имеет.
**Мера:** добавлен фильтр `NEUTRON_CAPTURE_RE` — подпись добавляется только если реакция содержит `(n,γ)`.
**Проверка:** в браузере (`javascript_tool`) — `SPECTRA.lines.filter(x=>x.reaction.includes('выход') &&
!/\(n[,;]\s*[γg]\)/.test(x.reaction))` дало 0 совпадений после фикса (было 2 из 3 проверенных примеров —
511 и 1460,82 кэВ — ложными).
**Класс:** поле, заполненное для ВСЕХ строк источника, применено без проверки применимости к подмножеству,
которому оно было предназначено — при добавлении новых производных полей из `bline_table.parse_lines` в
`lines_report.py` проверять область действия поля явно, не полагаться на то, что оно пусто/неприменимо там,
где не нужно.
**Опубликовано:** версия 23 той же ссылки.

## W-007. Словарь origin в stack.js — устаревший/неполный ключ процесса

**Найдено:** попутно, при подготовке EN-версии оверлея происхождения (22.09.2026).

`muIoni`, `muBrems`.

[stack.js](web/flight-dad-sgn/stack.js).
**Проверка:** самотест `node stack.js` — `SELFTEST PASS`; сверка полного множества `procname` из
`prod3_cat_all.csv` со словарём (Python `set` diff) — пусто.
**Класс:** ручной словарь-перечисление кодов Geant4-процессов не сверялся с фактическим списком
процессов в данных — при добавлении новых физ-процессов в модель проверять словарь тем же способом
(`set(procname) - set(dict.keys())`), не полагаться на память.
