## Зачем этот скилл

Задача: дан источник с известным паспортом (нуклид/цепочка, активность, дата поверки) и
его измеренный спектр на конкретном детекторе. Нужно разложить спектр по вкладам звеньев
цепочки, посчитать активность НЕЗАВИСИМО от паспорта (по модели детектора) и сравнить —
это калибровка МЕТОДА на известном ответе, не поиск неизвестного. Скилл — не готовая
программа, а операционная процедура + переиспользуемый код, наработанные на Th-232,
обобщённые под Ra-226 и проверенные внешним аудитом.

**Директива по умолчанию (09.08.2026): минимальное вмешательство ИИ.** Где есть
детерминированный критерий — решение принимает код, не агент. Агент подключается только
там, где критерия нет (см. «Где обязательно суждение» ниже). Не проектировать точки
ручного подтверждения там, где порог уже есть.

**ОБЯЗАТЕЛЬНО ПЕРЕД РАЗЛОЖЕНИЕМ ЛЮБОГО СПЕКТРА ЕРН (28.08.2026, указание оператора
«применяй при разделении спектра»):** читать `references/natural-series-equilibrium.md` —
какие соотношения активностей внутри рядов U-238 и Th-232 задавать, а какие подгонять.
Кратко, но чтение не заменяет: ториевый ряд равновесен (r_Th = 1,00 для природного сырья),
Tl-208/Bi-212 = 0,3594 структурно по ветвлению Bi-212 и подгонке не подлежит, f_Tn = 0 для
объёмных конструкций, дефицит дочерних радона f_Rn = 0,06–0,15 для бетона 100–300 мм
задаётся из литературы, а не подгоняется. Родители (Ra-226, Ac-228) на сцинтилляторе не
определяются — свободная подгонка загоняет их в ноль, и это ожидаемое поведение задачи, а
не дефект решателя.

## Архитектура: два метода на одном спектре

**Метод 1 (МК-шаблоны по нуклидам).** Каждое γ-испускающее звено цепочки — отдельный
Geant4-прогон полного распада ТОЛЬКО этого нуклида (`nucleusLimits` отсекает дочерние).
Сумма шаблонов при амплитуде, общей для всей ветви (допущение векового равновесия),
подгоняется к измеренному спектру (NNLS, пуассоновские веса + систематический пол).
Работает «из коробки» для цепочки в равновесии; для одиночного нуклида без цепочки
вырождается в одну амплитуду тривиально; для НЕравновесной цепочки нужна другая модель
подгонки (в контуре есть прецедент — разложение по нуклидам без допущения равновесия,
не задача этого скилла).

Макрос генерируется из таблицы нуклидов (`generate_isotope_macro.py`, см. ниже), не
пишется вручную по одному блоку на нуклид.

**Метод 2 (функция отклика × библиотека линий).** Каждой линии эмиссии (ENSDF, порог
интенсивности I_γ на нуклид) сопоставляется не эффективность пика, а весь депонированный
спектр монохроматического кванта (пик + континуум + вторичные), снятый на моноэнергетической
сетке той же геометрии. Отклики складываются с весами BR·I_γ/100 и подгоняются одной
амплитудой. Отдельно — сумм-пики каскадного совпадения (TCS) и K-рентген дочерних.

Оба метода — независимая реализация одной и той же физики двумя разными путями; их
схождение друг с другом и с паспортом — критерий доверия к модели детектора, не
навязанный результат.

## Поправка на истинное совпадение (TCS / F_B) — ядро метода 2

Для каскада E1→(общий уровень)→E2 наивная формула `P = BR·(I1/100)·(I2/100)·ε1·ε2`
double-считает заселение общего уровня, когда тот заселяется НЕ в 100 % распадов и
double-считает вклад партнёра каскада в истощение одиночных линий. Верная схема —
**два разных `ε` для двух разных ролей**, обе относительно одного и того же `F_B`:

```
# сумм-пик (весовая формула — берёт ПИКОВУЮ эффективность обеих линий)
P_sum = BR · (I1/100) · (I2/100) · eps_peak(E1) · eps_peak(E2) / F_B

# истощение одиночной линии Ei партнёром Ej (берёт ПОЛНУЮ эффективность партнёра)
depletion_i = BR · (I1/100) · (I2/100) · eps_peak(Ei) · eps_total(Ej) / F_B
```

где:

- **`F_B`** — суммарная депопуляция общего уровня = `Σ I_gamma·(1+CC)` по ВСЕМ
  исходящим гамма-переходам уровня (не только тем двум, что образуют пару), где `CC` —
  коэффициент полной внутренней конверсии перехода (безразмерный, электронный канал в
  дополнение к гамма-каналу). Источник CC — IAEA Live Chart of Nuclides, тот же запрос
  `decay_rads&rad_types=g`, поле `conversion_coeff` (раньше не сохранялось при выгрузке
  библиотеки линий — теперь отдельным инструментом, см. ниже).
- **`eps_peak(E)`** — эффективность регистрации именно в фотопике E (интеграл окна пика
  функции отклика).
- **`eps_total(E)`** — ПОЛНАЯ эффективность: вероятность зарегистрировать хоть какой-то
  сигнал от кванта E ГДЕ УГОДНО в спектре (сумма ВСЕЙ формы отклика — фотопик + комптон +
  вылет + аннигиляция + внешние эффекты; в коде — `resp(E)[0].sum()`, не третий элемент
  кортежа `resp()`, который даёт только `eps_peak`).

Смешивать роли — исходный источник ошибки: в сумм-пике нужна пиковая эффективность
ОБОИХ квантов (вероятность увидеть оба сразу в одном фотопике), в истощении — пиковая
СВОЕЙ линии и полная эффективность ПАРТНЁРА (вероятность, что партнёр унёс энергию
куда-то ещё в спектре, а не остался вместе с данным квантом в его пике).

### Откуда взялась текущая формулировка (закрытый аудит `df5d178`, 09.08.2026)

Первая версия конвейера содержала ДВЕ независимые ошибки в этой поправке, обе найдены
внешним аудитом и независимо им же перепроверены после фикса:

**Б1 — F_B без внутренней конверсии.** `F_B` считался как `Σ I_gamma` (только гамма-канал
депопуляции), без `(1+CC)`. Для низкоэнергетичных переходов в тяжёлых ядрах конверсия
может доминировать над гамма-каналом: на уровне 186,827 кэВ (Ac-228, переход 129,065 кэВ)
`I_gamma=2,42 %`, `CC=3,74` — исходящий гамма-поток без конверсии занижен в 4,5-4,7 раза
относительно входящего (баланс population=depopulation, проверено двумя независимыми
способами: прямое бета-питание уровня из IAEA `rad_types=bm` и `I_gamma·(1+CC)` из
`rad_types=g` — сошлись в пределах 4 %). Фикс: `F_B=Σ I_gamma·(1+CC)`. Аудитор
перепроверил тем же вечером собственным запросом к IAEA API (не по числам из отчёта) —
совпало дословно.

**Б2 — пиковая эффективность партнёра вместо полной в истощении.** Строка истощения
одиночной линии брала `eps_peak` партнёра каскада вместо `eps_total`. По Debertin &
Schötzig (1990), через Chehade (2007, IUP Bremen, магистерская диссертация, ур.
2.2-2.3, скачана и прочитана целиком, не пересказ): депопуляция линии γ1 партнёром γ2
идёт через `εT2` («the probability of γ2 being detected and appearing ANYWHERE in the
spectrum» — партнёр может унести энергию куда угодно по спектру, не только остаться в
своём фотопике). Численно на этой геометрии: `eps_total/eps_peak` от 1,06× (129 кэВ) до
7,53× (2614,511 кэВ) — недоучёт истощения тем сильнее, чем выше энергия партнёра (доля
полного поглощения в пике падает с энергией для NaI(Tl)). Баг существовал в ТРЁХ
независимых копиях формулы (`export_data.py`, `export_ra226_data.py`,
`ra226_method2_quicklook.py` — классическая copy-paste-до-фикса ошибка), исправлены все три.

Оба фикса — коммиты `2093b72` (Б1) и `ba43fff` (Б2) в этом репозитории. Итоговая формула
выше — не черновик и не «диапазон устарел вдвойне»: закрыта, запущена на живых страницах,
подтверждена аудитором независимым пересчётом.

## Мёртвое время, случайное суммирование, сверка с LSRM (10.08.2026)

Прочитан первоисточник — LSRM, «Прецизионные измерения. Образцовые и
калибровочные источники» (46 стр., `Дозиметрия\Книги\Нормы и методики\
Прецизионные измерения.pdf`, уже в RAG-корпусе `gamma-spectrum-analysis`
как `pretsizionnye_izmerenia`) — ✅, прочитано целиком (PyMuPDF, не
пересказ). Даёт три раздела: поправка на самопоглощение (см. отдельно
`selfabs_fit.py`/`kit_recalc.py`), истинное суммирование, случайное
суммирование. Ниже — сверка с этим конвейером и то, чего в конвейере
намеренно нет.

**Истинное (каскадное) суммирование — формулы СОВПАДАЮТ независимо.**
LSRM (стр. 23): `P12 = I1·I2/I2t·A`, где `I2t` — «полная интенсивность
вместе с конверсионными электронами» — это и есть `F_B` выше, другое
имя той же величины. Наша формула (раздел выше, закрыта аудитом
`df5d178`) получена независимо и совпадает по структуре. Их тест МАГАТЭ
(стр. 38-39, сравнение Genie2000/GammaVision/InterWinner/Hyperlab/
UniSampo/Angle/LSRM+TCCFCALC) показывает: БЕЗ коррекции каскадные
нуклиды (Na-22, Eu-152, Co-60) дают систематическую ошибку до −30 %
(A/A0 = 0,70-0,93), С коррекцией TCCFCALC — сходятся в пределах 1-4 %
(0,971-1,036). Подтверждает, что этот класс поправки НЕ опционален для
каскадных нуклидов на объёмных источниках.

**Метод 1 (МК-шаблоны по нуклидам) истинное суммирование не считает
ОТДЕЛЬНО — оно встроено физически.** Geant4 симулирует ПОЛНЫЙ распад
нуклида (все гамма-кванты каскада трекаются в одном событии через ту же
геометрию) — и потери на совпадение, и сумм-пики возникают в спектре
шаблона САМИ, без формулы `F_B`/`TCCFCALC`. Это структурное преимущество
метода 1 перед методом 2 (там TCS без явной F_B-поправки был бы обязан
провалиться так же, как некорректированные пакеты в тесте МАГАТЭ выше) —
и одновременно причина, почему метод 2 обязан считать `F_B`, а метод 1 —
нет. Асимметрия метода 2, которую стоит держать в уме: явная формула
`P_sum` ДОБАВЛЯЕТ сумм-пик, но НЕ вычитает потерю из одиночных линий-
партнёров сверх того, что уже сделано в `depletion_i` выше — то есть
поправка симметрична только если оба слагаемых (`P_sum` и `depletion`)
внесены в модель, что в этом конвейере так и есть (обе строки формулы
выше активны), но при переносе на новый конвейер это нужно проверять
явно, не считать «F_B само собой полное».

**Мёртвое время — коррекция ТОЛЬКО по живому времени (1 способ из 4).**
LSRM перечисляет 4 стандартных подхода (стр. 42): схемы антисовпадений,
метод генератора, фильтры, коррекция по живому времени. Этот конвейер
использует ИСКЛЮЧИТЕЛЬНО последний — `T = meas["live_s"]` (не
`real_s`) для нормировки модели и масштабирования фона везде
(`export_data.py`/`export_ra226_data.py`, `bg_scale_time = T/bg["live_s"]`).
Никакой отдельной эмпирической формулы вида `tm=A·Σyi+B·Σ(yi·i)`
(их стр. 43, калибруется по искусственно перегруженному Co-60) в
конвейере нет — доверяем полю `TLIVE` из шапки `.spe` как есть.
Оправдано при низкой/умеренной загрузке (в источниках этого конвейера
мёртвое время — десятые доли процента); при доле мёртвого времени
в единицы процентов и выше нужна отдельная проверка линейности живого
времени прибора, этот конвейер её не делает.

**Случайное суммирование (просчёты/pile-up) — не корректируется.**
LSRM отводит этому отдельный демонстрационный стенд (стр. 40-45,
намеренно перегруженный Co-60) — эффект существен именно при высокой
загрузке. В этом конвейере коррекции нет вообще, обоснование —
загрузка низкая (доли-единицы сотен CPS на объектах конвейера,
мёртвое время долей процента, на два+ порядка ниже демонстрационного
стенда LSRM). Гипотеза случайного суммирования как причины
необъяснённой структуры спектра ПРОВЕРЯЛАСЬ на живом источнике (Ra-226,
web-th232, задача #20, 10.08.2026) и отклонена по той же причине —
низкая загрузка делает эффект на порядки меньше наблюдаемого. **Если
новый источник имеет высокую загрузку (мёртвое время от единиц
процентов) — эту главу конвейера придётся писать заново, не
экстраполировать вывод «незначимо» с низкозагруженных источников.**

## Данные внутренней конверсии (`fetch_conversion_coeff.py`)

`data/conversion_coeff_sum_peak_levels.csv` — отдельная выгрузка IAEA Live Chart
(`decay_rads&rad_types=g`, поле `conversion_coeff`), покрывающая ВСЕ нуклиды ОБЕИХ
цепочек (не только те, что уже в `SUM_PEAKS`) — чтобы перебор кандидатов
(`enumerate_sum_peaks.py`) мог считать верный `F_B` для ЛЮБОЙ пары, не только уже принятой
вручную. Пишется `tools/fetch_conversion_coeff.py`, детерминирован по входному списку
нуклидов, коммитится как обычные данные.

**Полнота данных — проверяемое условие, не допущение.** Если для какого-то из исходящих
переходов уровня `CC` не найден (пустая строка API), `F_B` для этого уровня занижен на
неизвестную величину — считать его подозрительным (флаг `suspicious`/`cc_incomplete`),
не тихо принимать как есть.

## Перекрёстная проверка CC — второй независимый источник (09.08.2026)

внешний проект, не наш) навёл на второй источник CC того же семейства IAEA API, но по
ДРУГОЙ выборке: не `decay_rads` (гамма-линии КОНКРЕТНОГО распада, ключ — родитель), а
`gammas` (принятая схема уровней САМОГО НУКЛИДА, ADOPTED LEVELS ENSDF, ключ — нуклид,
родитель не нужен вовсе). `tools/fetch_adopted_gammas.py` тянет её для тех же 13
нуклидов в `data/adopted_gammas_cross_check.csv`.

**Роль — ТОЛЬКО кросс-проверка, не замена.** Полнота `tot_conv_coeff` у `gammas` ниже,
чем у нашего основного `decay_rads` (в выгрузке 09.08.2026: 367 строк с CC у `gammas`
против 302 у `decay_rads` — числа разного знаменателя, не сравнивать напрямую как
проценты). Ценность — независимая ENSDF-выборка того же CC, БЕЗ привязки к списку
родителей: подходит для нуклида, которого ещё нет в `NUCLIDES`.

**Сверка `tools/check_cc_cross_source.py` — ключ по ЭНЕРГИИ ПЕРЕХОДА, не по (нуклид,
уровень).** Причина: `decay_rads` ключует строку по РОДИТЕЛЮ (для перехода 129,065 кэВ
это `Ac228`), `gammas` — по владельцу схемы уровней, то есть ДОЧЕРНЕМУ (`Th228` для того
же перехода); плюс энергии САМИХ УРОВНЕЙ в двух выгрузках расходятся на 0,01-0,02 кэВ
(разные вводы одной оценки ENSDF), тогда как энергия перехода в обеих совпадает
практически всегда. Допуск сверки — 0,003 кэВ; при нескольких кандидатах на одной
энергии совпадение пропускается как неоднозначное, не гадается.

**Результат прогона 09.08.2026 (реальные числа, не иллюстрация):** 142 однозначных
совпадения из 302×367. Медиана расхождения **0,000 %** — подавляющее большинство
совпадает дословно (в т.ч. наш собственный Б1-пример: 129,065 кэВ, Ac228/decay_rads
CC=3,74 против Th228/gammas CC=3,74). Максимум — **71,4 %** на паре Bi212→Tl208, 473,0
кэВ (0,07 против 0,12) — систематически повышенные расхождения держатся именно
на ветви Bi212→Tl208: ВСЕ 6 её однозначных совпадений превышают 4 % (4,07-71,43 %),
похоже на грубое округление одного из источников для этой ветви конкретно, не на общую
проблему метода. Не расследовано глубже — не блокирует F_B (ветвь Bi212→Tl208 сейчас не
в `SUM_PEAKS` ни Th-232, ни Ra-226).

## Config-driven схема (что переносится в конфиг источника)

Инвентаризация (агенты, три независимых прохода по коду) показала: вычислительное ядро
(NNLS, матрица отклика, деконволюция ПШПВ, F_B) уже нуклид-агностично — весь хардкод был
в константах верхней части модуля. Схема `configs/<источник>.yaml` (по одному файлу на
источник — `th232.yaml`, `ra226.yaml`; НЕ единый `decay_chain.yaml`):

```yaml
source: {id, measured_xml_rel, chain_template_csv}
passport: {bq_per_kg, unc_pct, mass_g, passport_date, measured_date,
           half_life_years, days_pass_to_meas}
nuclides: [{key, label_ru, label_en, color, br, note_ru}, ...]
fit: {e_lo_kev, e_hi_kev}
library: {intensity_threshold_pct, lines: [{e_kev, i_pct, nuclide, note}, ...]}
sum_peaks: [{e1_kev, e2_kev, nuclide, i1_pct, i2_pct, note}, ...]
geant4:
  gps_region: {centre_mm, radius_mm, halfz_mm, confine_volume}
  isotope_runs: [{key, z, a, n_events, out_file, excitation_keV}, ...]  # excitation_keV опционален, по умолчанию 0 — нужен для изомерных состояний
```

Движок (`export_data.py` в референсной реализации) читает конфиг через переменную
`G4MODELS_SOURCE_CONFIG` (по умолчанию — конфиг текущего источника); менять код при
смене источника НЕ требуется, только конфиг. **Приёмочный тест любой правки движка —
числовой контроль**: выгрузка (JSON) до/после правки обязана быть побитово идентична
(md5), если правка не должна менять числа — рекурсивный diff по дереву JSON, не
визуальная сверка хвоста лога.

## Генератор макросов Geant4 из таблицы нуклидов

Язык макрокоманд Geant4 не знает переменных/циклов — блок на нуклид
(`nucleusLimits`/`gps/ion`/`outFile`/`beamOn`) в ручном макросе неизбежно копируется
постатейно, а GPS-регион пробы дублируется буквально в каждом файле. `generate_isotope_macro.py`
рендерит макрос из `geant4.isotope_runs` конфига: один источник истины, обязательная
директива `/process/had/rdm/thresholdForVeryLongDecayTime` пишется всегда (пропустить
нельзя — без неё долгоживущее первичное ядро молча не распадается, нулевой выход без
единой жалобы в логе).

Три гварда робастности, добавленные по итогам аудита Б4 (не блокировали действующие
цепочки Th-232/Ra-226, но защищают от тихой поломки на будущих источниках):

- пустой `isotope_runs` → явный `SystemExit`, не пустой макрос без единого `beamOn`;
- коллизия `out_file` между двумя записями таблицы → явный `SystemExit` с именами
  обеих записей, не молчаливая перезапись одного прогона другим;
- поле `excitation_keV` (по умолчанию 0) — для изомерных состояний, раньше энергия
  возбуждения в `/gps/ion` была жёстко захардкожена нулём для всех нуклидов.

**Воспроизводимость — проверяется реальным прогоном, не только побайтовым сравнением
текста макроса (Б3).** Первая версия генератора была сверена с прежним ручным макросом
только текстуально (диф побайтово идентичен) — этого недостаточно: опубликованные числа
на тот момент были посчитаны СТАРЫМ способом (два отдельных вручную написанных макроса,
один из которых уже не существовал в репозитории), новый генератор ни разу не гонялся
на реальных данных. Закрыто реальным Geant4-прогоном (11,6 млн распадов, 8 изотопов;
длительность прогона в логах/манифесте не зафиксирована — не приводить как факт) новым
сгенерированным макросом — числа сошлись со старыми в пределах статистики Монте-Карло.
Правило: смена генератора макроса — повод для реального прогона, не только для диффа
текста.

## Детерминированный перебор кандидатов суммирования

Критерий физического каскада — «конец перехода A = начало перехода B» (общий
промежуточный уровень, не общий начальный — последнее означает ветвление ОДНОГО уровня
на разные конечные, это НЕ каскад, оба кванта пары никогда не испускаются в одном акте
распада). Перебор по полной библиотеке линий детерминированно даёт ВСЕ пары-кандидаты
с этим свойством + верный `F_B` каждой (`enumerate_sum_peaks.py`, синхронизирован с
формулой Б1 — берёт тот же `data/conversion_coeff_sum_peak_levels.csv`). Кросс-проверка
на Th-232: перебор воспроизвёл 8/8 вручную принятых пар и НИ РАЗУ не предложил ни одной
из явно отклонённых fork-пар — структурное подтверждение, что критерий верный.

**Каскад через один пропущенный промежуточный переход (two-hop).** Прямой критерий
(«конец A = начало B») слеп к парам вида A→уровень1→(B, отдельно не в паре)→уровень2→C:
транзитивно A и C заселяют/покидают общую цепочку уровней, но общего уровня напрямую у
них нет — их находит отдельный проход `enumerate_two_hop()` (поиск путей длины 2 по
графу уровней). Физика этих пар отличается от прямых (два разных промежуточных
перехода, не один), поэтому функция намеренно НЕ считает им score/F_B автоматически —
только перечисляет кандидатов для ручной проверки. Флагманский пример (Tl-208,
277,371+2614,511 кэВ, общая цепочка через уровень 2891,9 кэВ) должен быть виден в выводе
по умолчанию — если вывод отсортирован по нуклиду, а не по паре I1·I2 глобально, пример
может оказаться погребён за сотнями алфавитно более ранних пар другого нуклида
(реальная находка при разработке — сортировка исправлена на глобальный ранг по I1·I2).

**Где обязательно суждение (не автоматизируется тривиально):** отбор кандидата в SUM_PEAKS
требует перекрёстной проверки НЕЗАВИСИМЫМ источником (LNHB/DDEP против ENSDF) — без
второго источника решение о включении пары остаётся ручным. Скрипт перечисляет и считает,
не решает. Кандидат с `cc_incomplete`/`suspicious` (см. выше) — тем более не принимать
без проверки вручную, отсутствие данных о конверсии маскируется под «низкий F_B»
одинаково с реальным низким F_B.

## Таксономия текста веб-страницы (пять форматов, не один «конфиг»)

Текст страницы — НЕ одна категория «вынести в конфиг»: у него пять разных ролей, и формат
должен быть разный.

| Роль | Пример | Формат |
|---|---|---|
| UI-хром | заголовки вкладок, кнопки | shared-литерал, не трогается |
| Описание метода | «метод 2 — библиотека + сумм-пики» | набор параметризованных предложений, выбираемых по варианту движка (не свободная генерация) |
| Описание прибора | геометрия детектора | фрагмент НА ДЕТЕКТОР, переиспользуется всеми источниками на нём |
| Описание источника | паспорт, дата, матрица | шаблон-с-токенами на ИСТОЧНИК |
| Вывод/сравнение с паспортом | «сходятся в пределах…» | **НИКОГДА не конфиг и не шаблон** — заново пишется по актуальным числам, проходит свой аудит перед публикацией |
| Библиография/ИИ-заявление | ENSDF/LNHB, роли ИИ | shared-литерал |

Строка «вывод/сравнение» — самое частое место повторной ошибки: формулировка,
зафиксированная один раз, протухает при следующем физическом фиксе (в этом же проекте
ломалась трижды за сессию, пока не был принят принцип «пишется заново, не редактируется»).

**Перечисление сущностей (нуклидов и т.п.) в прозе — токеном, не текстом.** Хардкод списка
мимо системы токенов `{{}}` — реальная найденная ошибка (t-method popup называл 8 нуклидов
текстом, страж «числа цифрами в разметке» такую форму не ловит вовсе); молча расходится
при смене состава источника.

## Валидация входов — ДО построения конвейера (ретроспектива Ra-226, 10–11.08.2026)

Хронология линии Ra-226: дни работы на негодном файле (-19, снят с конвейера),
затем перекалибровка низа шкалы, затем ТРИ разворота интерпретации расхождения
с паспортом. Ни одна из этих ошибок не была кодовой — все входного уровня.
Порядок валидации, который бы их снял ДО начала:

**1. Файл измерения.** Прежде чем строить на файле что-либо: live/real/мёртвое
время; argmax реперных линий против заводского полинома ПО ВСЕМУ диапазону,
включая низкоэнергетичный край. Бесплатный физический якорь есть в любом
измерении в свинцовом укрытии: К-рентген свинца защиты (Kα 73–75, Kβ 85–87 кэВ,
у фона взвешенное ~77); у образца с Pb-214/Bi-214 — их собственный К-рентген
(74,8–90,9 кэВ, взвешенное ~79). Расхождение якоря с полиномом больше ~половины
ПШПВ — файл под вопросом, шкала требует поправки. Негодный файл заносится в
чёрный список ЯВНО (задача + remarks с причиной), не молча заменяется — иначе
следующая сессия его переоткроет.

**2. Шкала.** Центроиды с простой моделью подложки (гаусс+линия, центр масс)
ВРУТ на кривом комптоновском континууме — на линии Ra-226 те же методы давали
ложные уходы 3–15 кэВ на точках, независимо проверенных как верные. Реперы —
по argmax + внешняя физика (IAEA NDS), не по подгонке. Поправка шкалы —
ЛОКАЛЬНАЯ (квадратик по якорям с smoothstep-сшивкой к заводской кривой);
глобальный рефит без надёжного верхнего якоря запрещён — проверено численно:
квадратик, идеальный на 77–352 кэВ, уводит 2204 кэВ на +313 кэВ. Применённая
поправка ОБЯЗАНА попасть в метаданные выгрузки (см. ловушку рассинхрона meta).

**3. Паспорт (опорное значение).** Прежде чем сравнивать с паспортом —
установить, ЧТО он измеряет: методику аттестации и прослеживаемость. Ra-226
аттестуют ПО ДПР (Pb-214/Bi-214) или альфа-счётом — «активность Ra-226» в
паспорте не равна активности по линии 186,211 кэВ, и при постоянной утечке
радона паспорт сам подавлен той же утечкой, что и текущее ДПР-измерение.
Непроверенное допущение о методике аттестации стоило линии Ra-226 двух
неверных интерпретаций подряд (сначала «направление не соответствует утечке»,
потом отмена — оба разворота от одного корня). Методика не установлена
документом — писать в вывод как ДОПУЩЕНИЕ явно, с перечнем того, что от него
зависит.

## Разрезы по группам нуклидов и погрешности производных величин

**Разрез ДПР против родителя** — штатная диагностика утечки радона для цепочки
Ra-226: две свободные амплитуды (Pb214+Bi214 против Ra226+хвост), ничего не
фиксировать; доля, теряемая из счётной геометрии, f = 1 − ДПР/Ra-226.
Терминологическая дисциплина: это НЕ «коэффициент эманирования» (тот — доля
радона, покидающая зёрна матрицы В сосуд, меряется продувкой; Povinec 2015) —
сравнивать только с литературой по той же величине (герметизация Маринелли:
Syam 2020, Lim 2021). Имя величины = измеряемая величина, иначе сравнение
с литературой сопоставляет разное.

**Нулевые базисы.** Нуклид без единой линии в библиотеке даёт нулевой столбец —
группировки, различающиеся только такими нуклидами, дают ОДИН И ТОТ ЖЕ фит под
разными именами. Проверять побитовым сравнением амплитуд; два «независимых
теста» с совпадающими числами — один тест, писать это явно, не выдавать
переименование за подтверждение.

**Погрешность производной величины из совместного фита занижена НА ПОРЯДОК
формальной статистикой.** На Ra-226: f заявлялась ±3,7% (NNLS-статистика),
скан по границам окна подгонки дал 7,7–23,0%. Обязательный шаг перед
публикацией любого отношения амплитуд: прогнать конвейер на 5–6 комбинациях
E_FIT_LO/E_FIT_HI, публиковать рабочую точку + диапазон. Ковариация амплитуд и
масштабирование на √(χ²/ν) — поправки второго порядка рядом с систематикой
окна (измерено: ~2% и ×1,96 против ×5 разброса) — упоминать, но не выдавать
их учёт за решение проблемы. Вырожденное окно (ключевая линия целиком вне
диапазона) даёт амплитуду 0 и NaN в производных — гвард обязателен (см.
ловушку allow_nan).

## Сверка библиотеки линий с LNHB (подъём 📗 → ✅)

Отобранная библиотека (I≥порога) сверяется построчно со второй независимой
оценённой базой LNHB/DDEP. Механика, отработанная на Th-232 и Ra-226:

1. PDF-таблицы `lnhb.fr/nuclides/<Nuclide>_tables.pdf` качать `curl` напрямую,
   разбирать `pymupdf` — НЕ пересказ WebFetch (пересказ ≠ прочитано).
2. Сверка по энергии (допуск ±0,5 кэВ на округление) и интенсивности; в отчёт —
   дословные строки таблицы, не пересказ. В PDF LNHB у одной линии может быть
   ДВЕ близкие записи на разных страницах (Bi-214 1729,611/1729,595) — выбирать
   по совпадению энергии, не по удобству числа.
3. Массовую сверку делает стерильный субагент с правилами sci-search, вписанными
   в ТЗ дословно; его отчёт НЕ принимается на слово — актор сам перечитывает
   минимум 2 контрольные точки (главную линию + любую, где субагент отметил
   расхождение) прямым чтением того же PDF.
4. Разметка уровня — ПО-АРТЕФАКТНО: ✅ поднимается только для сверенных линий;
   пары суммирования, полная (непороговая) библиотека, CC — остаются на своём
   уровне, в одну общую пометку страницы не сливать.
5. Результат — в корпус sci-search (агрегированно по нуклиду) и полной таблицей
   в remarks-журнал.

## Свод ловушек (кровью, конкретные строки — по референсной реализации)

- **CRLF vs Edit-инструмент.** Многострочный `old_string` у Edit ненадёжно матчится в
  CRLF-файлах этого репо. Рабочий обход: Python-хирургия — `io.open(path, encoding="utf-8",
  newline="")` (сохраняет CRLF как есть), найти уникальные ASCII-якоря `str.find()`,
  собрать замену `"\r\n".join([...])`, записать тем же `newline=""`. Проверить
  `py_compile`/`node --check` после. Однострочный `old_string` (без `\n` внутри) у Edit
  работает нормально в тех же файлах — проблема именно в многострочном совпадении.
- **Forward-reference NameError при модульных top-level вычислениях.** Модуль конвейера
  исполняется целиком при импорте; новый код на верхнем уровне не должен ссылаться на
  константы/функции, определённые НИЖЕ в файле — либо переносить код после определений,
  либо строить нужное из уже доступного (ранние константы, builtins).
- **Молчаливо не тот build-каталог.** Диагностические скрипты по умолчанию смотрят в
  `<репо>/build/<Детектор>` (почти пустой), если переменная `G4MODELS_BUILD_<ДЕТЕКТОР>`
  не задана — не «таймаут», а тихо не туда. Всегда задавать явно.
- **`window.<ГЛОБАЛЬ>`, не общий `window.D`.** Данные страницы обычно читаются внутри
  замыкания IIFE в переменную вроде `D`; снаружи (консоль/javascript_tool) доступен только
  внешний глобал (`window.G1S`, `window.RA226` и т.п.), не внутреннее имя. Проверять по
  факту, не искать перебором по всем ключам `window`.
- **Магическое число потолка гистограммы.** Число каналов/потолок энергии, откалиброванные
  под максимальную линию ТЕКУЩЕГО набора нуклидов, ломаются молча при цепочке с более
  высокой линией или суммарным пиком — выводить из конфигурации набора, не хардкодить.
- **Коллизия имён выходных файлов между независимыми макросами.** Несколько макросов,
  пишущих в файлы с одинаковыми именами разной статистикой (один «штатный», другой —
  «более точный повтор»/«добор») — молчаливая перезапись без единой ошибки, порядок
  запуска решает, какие данные реально легли в build. Решение — либо единый генератор
  с явным гвардом на коллизию (см. выше), либо явное пространство имён на макрос/цель.
- **Отсутствие `thresholdForVeryLongDecayTime`.** По умолчанию порог 1 год — долгоживущее
  ПЕРВИЧНОЕ ядро (Ra-228 5,75 г, Th-228 1,9 г, K-40, Ra-226) убивается, не распавшись,
  молча, без единой жалобы в логе. Обязательная строка в КАЖДОМ макросе распада.
- **Область розыгрыша GPS не покрывает пробу.** `confine` лишние точки отбрасывает, но
  недостающих не создаёт — непокрытая часть пробы не облучается, эффективность выходит
  завышенной, молча. Сторож в модели (`CheckConfinement`) ловит непокрытие ПОСЛЕ прогона,
  не до — синхронизация региона с реальной геометрией сосуда всё равно ручная.
- **Один и тот же товарный номер — разный состав.** Под одним каталожным именем набора
  поверки может быть ДВЕ разные версии материала (разных лет поверки) — верить массе/
  объёму/дате из построенной геометрии, а не имени.
- **Приватные паспортные данные — только через выделенный env-механизм.** Репозиторий
  контура уже несёт `paths.passport(detector)`/`paths.measured(detector)`
  (`G4MODELS_PASSPORT[_<ДЕТЕКТОР>]` / `G4MODELS_MEASURED`) с понятным `SystemExit`, если
  данных нет — новый источник обязан идти через них, не заводить свой литерал/путь в
  обход.
- **F_B без внутренней конверсии — почти всегда занижен, не приближение (Б1).** Если
  библиотека линий несёт только `line_type=gamma/xray` без `conversion_coeff`, сумма
  ИСХОДЯЩИХ гамма-интенсивностей уровня может быть МЕНЬШЕ суммы ВХОДЯЩИХ — это невозможно
  при балансе, если гамма не единственный канал депопуляции. Признак: проверять баланс
  вход/выход явно, не принимать заниженный F_B молча.
- **Пиковая эффективность партнёра каскада в формуле истощения — недоучёт, растущий с
  энергией (Б2).** `eps_total/eps_peak` не константа около 1 — на этой геометрии до
  7,5× на верхнем краю рабочего диапазона (2614,511 кэВ). Если истощение линии от
  высокоэнергетичного партнёра выглядит подозрительно малым — первым делом проверить,
  какая эффективность подставлена.
- **Two-hop каскады невидимы прямому критерию смежности.** Пара может быть физически
  валидной (транзитивная цепочка уровней), но не давать общего НЕПОСРЕДСТВЕННОГО уровня
  — нужен отдельный проход поиска путей длины 2, не расширение порога прямого критерия.
- **`json.dump` без `allow_nan=False` — NaN тихо доезжает до страницы.** NaN — невалидный
  JSON, но валидный JS-идентификатор: обёртка `window.X = {...NaN...};` парсится, деплой
  не падает, страница молча печатает «NaN Бк». Реальный путь: вырожденное окно подгонки
  (линия вне диапазона) → амплитуда 0 → производная NaN. Всегда `allow_nan=False` —
  падать громко на экспорте, не публиковать мусор.
- **Метаданные обязаны отражать применённую обработку.** Поправка шкалы применялась двумя
  строками выше, а в `meta.energy_correction` уезжал хардкод `None` — выгрузка ЗАЯВЛЯЛА
  отсутствие поправки, которая есть. Рассинхрон код/метаданные ловится только аудитом;
  правило: каждый шаг обработки, влияющий на оси/числа, пишет свой словарь в meta из ТЕХ
  ЖЕ констант, которыми выполнен.
- **Заполнение мёртвого поля активирует мёртвый код.** `energy_correction: None → dict`
  оживило JS-блок, написанный под СТАРУЮ, давно отменённую форму этого поля — вкладка
  вживую печатала «E = NaN + NaN·E». Правки — тоже код: после КАЖДОЙ правки формата
  данных перепроверять рендер в браузере, даже если правка «только добавила поле».
- **Рукописный текст рядом с живым числом рассинхронизируется.** Дважды на одной линии:
  комментарий держал числа окон от снятого файла -19 рядом с живым caveat для -18.
  Пояснение, написанное руками под конкретный прогон, обязано либо строиться из тех же
  переменных (%-подстановка), либо нести дату и явный маркер «переписать при смене входа».
- **Починил референс — grep клоны.** Находка R44 («амплитуда фона» → «поправка
  континуума») исправлена в `g1s-th232.js`, а копия в `ra226.js` осталась старой и дожила
  до замечания оператора. После фикса в референсной реализации — grep по репо на тот же
  паттерн, чинить все вхождения одним заходом.
- **`cp` в docs стирает `?v=` кэш-метки.** Исходник их не несёт — после каждого копирования
  `sed` заново, ВСЕ места (css/data/scripts). Забытая метка = пользователь смотрит старую
  версию и репортит уже починенное.
- **Футер: дата публикации + редакция (git SHA ссылкой на коммит) — обязательны** на
  каждой публичной странице (правило оператора 11.08.2026, постоянное). SHA в тексте
  отстаёт на один коммит от факта — это принятый компромисс, не чинить amend'ом.

## Автоматизация уроков (v1.4.0, ТЗ внешнего аудита 11.08.2026)

Каждый пункт — что стало кодом/guard'ом (проверяемо: файл, функция, self-test),
что осталось процедурой (с явным обоснованием почему не автоматизируется тривиально).

**Guard ширины окна якоря против ПШПВ (п.6) — код.** `export_data.py.
assert_anchor_window_ok(window_half_kev, E_kev, max_mult=0.7, label=...)`:
падает `SystemExit`, если полуширина окна центроида/argmax шире 0,7×ПШПВ
прибора на этой энергии. Этот класс ошибки (наивно широкое окно тянет якорь
к соседнему континууму) ловился в одной сессии МИНИМУМ трижды порознь —
правило было прозой, агент забывал применять заново на каждом новом якоре.
Юнит-проверен (принимает 0,6×ПШПВ, отклоняет наивные ±105 кэВ на K-40).
Новый калибровочный код ОБЯЗАН вызывать этот guard явно — не полагаться
на память о правиле.

**rad_types=g,x по умолчанию + проверка полноты (п.1) — код.**
`tools/fetch_line_library.py` — реюзабельный fetcher, ОБА `rad_types`
всегда одним вызовом на нуклид (не флагом, который можно забыть),
`check_completeness()` требует хотя бы одну строку `rad_types=x` с I≥1%
для нуклидов с EC/IT/β⁺ в явно переданном режиме распада — иначе
`SystemExit` с именем нуклида, не тихий пропуск. Юнит-проверен на живом
запросе (Eu-152 EC → 30 рентген-строк, полнота пройдена). Прежняя ad-hoc
сборка библиотеки AmTiCsEu (данные уже в data/ensdf_amticseu_chain_lines.csv,
дыра найдена и закрыта оператором в рамках Теста 3, §10 remarks) не имела
персистентного инструмента — теперь есть, для СЛЕДУЮЩЕГО источника
дыра невозможна структурно, не «агент не забудет».

**Сумм-перебор с аннигиляцией (п.9) — код.** `tools/fetch_beta_plus_feeds.py`
(IAEA `rad_types=bp`, поле `daughter_level_energy` — уровень, заселяемый
ИМЕННО β⁺-ветвью, не EC) + `enumerate_sum_peaks.py.
enumerate_annihilation_pairs()` — прежний прямой критерий («конец A=начало
B») структурно слеп к 511 кэВ (нет ядерного уровня); здесь уровень паре
задаёт сама β⁺-ветвь. Юнит-проверен на живых данных AmTiCsEu: нашёл
Ti44chain 511,000+1157,022, score=94,27, F_B=99,89 — тот же кандидат,
что раньше находился только вручную (amticseu-remarks.md, разбор Sc-44).
KEY в `--nuclide` обязан совпадать с ключом группы в конфиге/CSV
переходов, не с именем физического нуклида — иначе не сматчится (реальная
ошибка первого прогона этой сессии, поймана сразу по пустому выводу).

**Автотест формулы χ² по полосам (п.3) — код, поймал реальный баг
СРАЗУ.** `export_data.py.chi2_by_energy_bands(y, cols, coef, sig,
e_of_ch_sel, bands)` + `_self_test_chi2_by_energy_bands()`
(`python export_data.py --selftest`). При разработке ЭТОЙ функции
self-test СРАЗУ поймал расхождение (88,496849 vs 88,497384, ~6e-6
относительных) — реконструкция σ по финальной модели НЕ тождественна
σ, которым `fit_amplitudes()` реально считает chi2 (σ заморожен
ПОСЛЕ первого прохода NNLS, IRLS-приём, финальная модель — уже после
второго). Fix: `fit_amplitudes()` получил опциональный `_sig_out`
(out-параметр, не ломает существующие вызовы) — отдаёт ТОТ ЖЕ массив σ,
чтобы band-разбивка не гадала. Урок: даже собственный self-test пишущего
агента не гарантирует правильность с первой попытки — гарантирует, что
расхождение НЕ уйдёт в прод молча (self-test упал бы на CI/при следующем
запуске, не только повезло поймать в разработке).

**Один источник истины физконстант (п.5) — частично, процедурно.**
T½ Sc-44 (4,042 ч, IAEA NUBASE2020) была верна в HTML/конфиге, но
устаревшее значение (3,97 ч, из памяти) осталось в комментарии
НЕсвязанного скрипта `analysis/kit_mixture.py` — исправлено точечно.
Единого программного источника констант (все читают из одного файла/
поля) для ЭТОГО класса величин НЕ заведено — T½ Geant4 берёт из
СОБСТВЕННОЙ ядерной базы (RadioactiveDecay module), не из конфига
пайплайна; текст страницы — из константы в export-скрипте. Три места,
не одно, физически (движок Geant4, конфиг, текст) — единый источник
истины возможен только для конфиг/текст пары, не для движка. Сделано.

**Пересмотр схемы-сильнее-физики (п.2) — процедурное правило, не
автодетектор.** Единственный известный экземпляр (511 кэВ, `load_
full_library()` фильтровал по наличию `start_level_energy`/
`end_level_energy` у ВСЕХ строк) уже исправлен (§10 remarks). Общего
автоматического детектора «где ещё требуется поле не по делу»
не существует — контрпример: `enumerate_sum_peaks.load_transitions()`
делает ТО ЖЕ САМОЕ (требует level) намеренно (это критерий каскада, не
дефект) — программно нельзя отличить «поле требуется, потому что
семантически необходимо» от «поле требуется по лени схемы». Правило:
при добавлении нового фильтра-по-полю в код сборки библиотеки —
явно спросить «это отсекает по ФИЗИКЕ или по УДОБСТВУ схемы», записать
ответ в комментарий рядом. Процедура, не код — обоснованно (см. выше).

**Калибровка через вендорскую таблицу пиков (п.7) — ЧАСТИЧНО не
подтвердилось на практике, важная поправка.** `lsrm_peaks_table`
из шапки .spe (`spe.extras["lsrm_peaks_table"]`) — реальный, ранее не
использованный как ПЕРВИЧНЫЙ источник, только для сверки постфактум.
Прямая проверка (11.08.2026, эту же сессию): замена якоря Am-241 с
argmax (канал 24,3) на вендорский пиковый фит той же линии (канал
25,456±0,247) УХУДШИЛА подгонку — χ²/ν метод 1: 14,95→21,11,
Am-241/паспорт: 1,302→1,644 (дальше от 1, не ближе). Причина: вендор
фитит ОДНОЙ гауссианой тот же блендированный горб (Am-241+К-рентген
Ti/Pb), что и наш argmax — не гарантированно менее смещён. Правка
ОТКАЧЕНА, прод не тронут. **Вывод: вендорская таблица — штатный
источник КАНДИДАТОВ якорей (не переоткрывать руками), но НЕ
автоматически принимаемая истина.** Новое правило (расширяет п.6):
любой новый якорь (откуда угодно — argmax, вендор, скриншот)
принимается ТОЛЬКО если реальный прогон конвейера показывает
улучшение (χ²/ν не растёт, ratio_to_passport не уходит дальше от 1) —
иначе не публиковать, независимо от авторитетности источника.

**Критерий приёмки автономности (треб. 3) — определён, не пройден
задним числом.** Следующий тест на новом источнике обязан вестись со
счётом раундов вмешательства оператора по двум категориям: (а)
законное суждение по природе задачи (отбор сумм-пиков без независимого
источника — уже помечено в SKILL.md как ручное, п. «Где обязательно
суждение» выше) и (б) всё остальное. Цель — (б)→0. Тест 3 дал ~8
раундов преимущественно категории (б) — НЕ пересчитывается задним
числом (пересчёт по памяти = гипотеза, не факт), считать с НУЛЯ на
следующем источнике. До прохождения этого критерия — не публиковать
новый тест как «финальный»/«самостоятельный» (п.12, страница
проверена — ярлык уже не несёт этих слов).

**Пост-билд линтер числа-в-тексте-против-JSON (п.4) — ОТЛОЖЕНО,
обоснование.** Требует ретрофита: либо разметки чисел в HTML спец-
атрибутом (`data-json-path="method1.groups.Am241.A_Bq"`), которой
сейчас НЕТ ни на одной из трёх живых страниц (текст — литерал,
формируемый JS-шаблоном на лету, не статический HTML с числами),
либо эвристики «найти похожее число рядом с похожим словом» —
ненадёжно (пример: «14,95» может относиться к χ²/ν ИЛИ к какой-то
другой величине с тем же значением). Правильное решение — архитектурное
(ввести конвенцию разметки для ВСЕХ будущих чисел в тексте), не
однодневная утилита поверх текущей вёрстки. Задача зарегистрирована
(#14, контур GEANT4), не отменяется, но переносится на следующий раунд
переписывания текстового слоя, не на этот.

**Устойчивая модель мультиплета (п.10) — ОТЛОЖЕНО, обоснование.**
Паттерн (близко стоящие линии дают смещённый argmax/центроид)
встретился дважды на независимых источниках (Th-232 300,087/860,557;
AmTiCsEu Sc-44 1157,02) — паттерн реальный, не случайность одного
спектра, п.10 прав. Но обе испытанные ЭТОЙ сессией попытки (ступенчатая
подложка, деконволюция без ступени) дали статистически ХОРОШИЙ фит с
ЛОЖНЫМ смещением −3…−11 кэВ на чистых линиях — то есть «добавить ещё
один компонент к фиту» не решение, а другой способ обмануться
уверенно. Совместная модель нескольких близких пиков (не argmax
одного, учёт формы соседей явно) — нужна, но это отдельная
разработка с собственной валидацией на синтетике ДО применения к
реальным данным, не однодневная правка. Оценка объёма — следующая
сессия, до неё паттерн остаётся раскрытым как открытый вопрос на
странице (текущая практика), не тихо обходится.
